## 1. 개요

본 과제는 강의에서 제공한 취약한 기준 구현체(`ugonfor/secure-coding`, 이하 "기준 코드")를 바탕으로, 소프트웨어 개발 생명주기(요구사항 분석 → 시스템 설계 → 구현 → 체크리스트 작성/테스트 → 유지보수) 전 과정을 직접 수행하며 시큐어 코딩을 적용하는 것을 목표로 한다. 기준 코드는 회원가입/로그인/프로필/상품/신고/전체채팅 기능이 동작은 하지만 의도적으로 보안 요소가 빠져 있었고, 본 프로젝트는 해당 기능을 요구사항에 맞게 재설계·구현하면서 보안 약점을 제거하고, 강의에서 직접 설계하도록 요구한 **송금, 검색, 관리자** 기능을 새로 추가했다.

## 2. 요구사항 분석

### 2.1 기능 요구사항 (강의 slide p.22, p.35 기준)

| 대분류 | 요구사항 |
|---|---|
| 회원 관리 | 가입/로그인, 프로필(소개글/비밀번호) 관리, 아이디 중복 불가 |
| 상품 관리 | 등록/조회, 목록에는 이름만 노출 → 클릭 시 상세 페이지 |
| 소통 | 전체 채팅, 1:1 채팅 |
| 신고/제재 | 신고 사유 필수, 일정 횟수 이상 신고 시 상품 차단 / 유저 휴면 전환 |
| 송금 | 유저 간 송금 (직접 설계) |
| 검색 | 상품 검색 (직접 설계) |
| 관리자 | 플랫폼 전 요소 관리 (직접 설계) |

### 2.2 직접 설계한 요구사항 상세

기준 슬라이드(p.24~28)에서 설계가 주어지지 않은 세 기능에 대해 아래와 같이 요구사항을 도출했다.

**송금**
- 로그인한 사용자만 송금 가능해야 한다.
- 자기 자신에게는 송금할 수 없어야 한다.
- 잔액이 부족하면 송금이 거부되어야 한다.
- 정지(휴면)된 사용자에게는 송금할 수 없어야 한다.
- 모든 송금 내역은 감사 가능하도록 로그로 남아야 한다.
- 상품 구매는 "송금 + 상품 상태 변경(판매완료)"이 하나의 트랜잭션으로 처리되어야 한다.

**검색**
- 로그인한 사용자는 상품명/설명으로 상품을 검색할 수 있어야 한다.
- 차단된 상품은 검색 결과에 노출되지 않아야 한다.
- 검색어에 의한 SQL Injection이 불가능해야 한다.

**관리자**
- 관리자 계정은 소스코드에 하드코딩되지 않고 별도 절차(환경변수)로 생성되어야 한다.
- 관리자는 회원(정지/해제), 상품(차단/해제/삭제), 신고(검토/기각), 거래 내역을 조회·관리할 수 있어야 한다.
- 관리자가 아닌 사용자는 관리자 페이지에 접근할 수 없어야 한다(403).
- 관리자의 주요 조치는 감사 로그로 남아야 한다.

## 3. 시스템 설계

### 3.1 아키텍처

기준 코드와 동일하게 프론트/백엔드를 분리하지 않고, **Flask + Jinja2 서버 렌더링 + Flask-SocketIO** 단일 애플리케이션으로 설계했다. 별도 API 서버·SPA 클라이언트로 나눌 경우 인증 토큰 관리, CORS 등 새로운 보안 이슈가 추가되는 반면, 본 과제의 핵심은 "이미 만들어진 기능에서 보안 약점을 찾고 고치는 것"이므로 구조를 단순하게 유지하는 쪽을 선택했다.

```
server/
  app.py            # Flask 앱 팩토리, 보안 헤더/에러 핸들러
  config.py         # 환경설정 (SECRET_KEY, 세션 쿠키 옵션, 정책 상수)
  extensions.py     # db, login_manager, csrf, socketio, limiter
  models.py         # User/Product/Report/Conversation/Message/Transaction/AuditLog
  security.py       # 비밀번호 해시, 아이디/비밀번호 형식 검증
  forms.py          # Flask-WTF 폼 (서버측 검증 + CSRF)
  blueprints/
    auth.py         # 회원가입/로그인/로그아웃
    profile.py       # 마이페이지, 공개 프로필
    products.py      # 상품 CRUD + 검색
    chat.py          # 채팅 라우트 + SocketIO 이벤트
    reports.py       # 신고 + 자동 임계치 제재
    transfers.py     # 송금/구매
    admin.py         # 관리자 기능
  scripts/seed_admin.py  # 관리자 계정 시드 (환경변수 기반)
  templates/, static/
```

### 3.2 페이지 설계

기본 페이지, 회원가입/로그인, 마이페이지, 공개 프로필, 상품 목록(+검색), 상품 등록/수정/상세, 전체 채팅, 1:1 채팅, 신고, 송금, 거래내역, 관리자(대시보드/회원/상품/신고/거래) 페이지로 구성했다.

### 3.3 데이터베이스 설계

| 테이블 | 주요 컬럼 |
|---|---|
| `user` | id, username(unique), password_hash, bio, balance, role, status, report_count, failed_login_count, locked_until |
| `product` | id, title, description, price, seller_id(FK), status, report_count |
| `report` | id, reporter_id(FK), target_type, target_id, reason, status, **UNIQUE(reporter_id, target_type, target_id)** |
| `conversation` | id, user_a_id(FK), user_b_id(FK), **UNIQUE(user_a_id, user_b_id)** |
| `message` | id, room, sender_id(FK), content, created_at |
| `transaction` | id, sender_id(FK), receiver_id(FK), amount, kind(transfer/purchase), product_id(FK, nullable) |
| `audit_log` | id, actor_id(FK, nullable=시스템 자동조치), action, target |

기준 코드 대비 `balance`(잔액), `role`/`status`(권한·제재 상태), `report_count`/`failed_login_count`/`locked_until`(제재·잠금 근거), `conversation`/`transaction`/`audit_log`(신규 기능 및 감사 로그)를 추가 설계했다.

## 4. 시스템 구현

Flask-SQLAlchemy(ORM), Flask-Login(세션), Flask-WTF(폼 검증+CSRF), Flask-SocketIO(채팅), Flask-Limiter(rate limit), bcrypt(해시)를 사용했다. 각 블루프린트는 기능 단위로 분리했고, 소유자/권한 검증이 필요한 라우트에는 명시적으로 조건문을 두어 403을 반환하도록 구현했다. 구현 세부 내용은 저장소 코드와 아래 5장(체크리스트)에서 항목별로 근거 파일을 함께 표기했다.

## 5. 체크리스트 작성 및 테스트

### 5.1 체크리스트

전체 체크리스트는 [`docs/security_checklist.md`](security_checklist.md)에 7개 섹션(회원가입/상품/채팅/신고/**송금**/**관리자**/전체 시스템), 총 34개 항목으로 정리했다. 각 항목은 상태(✅ 구현 / ⚠️ 운영 환경에서 추가 필요)와 구현 위치(파일/함수)를 함께 표기했다.

### 5.2 실제 테스트 (수행 결과)

로컬에서 서버를 구동한 뒤 `curl` 및 `python-socketio` 클라이언트로 아래 시나리오를 직접 실행하여 확인했다.

| 테스트 시나리오 | 기대 결과 | 실제 결과 |
|---|---|---|
| CSRF 토큰 없이 상품 등록 POST | 400 거부 | ✅ 400, "CSRF token is missing" |
| 로그인 폼에 `' OR '1'='1` 입력 | 로그인 실패(SQLi 무력화) | ✅ 파라미터 바인딩으로 일반 로그인 실패 처리 |
| 회원가입 아이디에 `<script>` 입력 | 형식 검증 실패 | ✅ "아이디는 영문/숫자/밑줄 3~20자만 가능" 오류 |
| 상품 설명에 `<img onerror=...>` 입력 후 상세 페이지 조회 | HTML 이스케이프되어 스크립트 미실행 | ✅ `&lt;script&gt;...` 로 이스케이프되어 렌더링 |
| 타인의 상품 수정/삭제 시도 | 403 | ✅ 403 |
| 상품 검색(부분 문자열) | 일치 상품만 반환, 없으면 빈 목록 | ✅ 정상 동작 |
| 상품 구매(송금 연동) | 구매자 잔액 차감, 판매자 잔액 증가, 상품 상태 `sold`로 변경, 거래내역 기록 | ✅ 정상 동작 |
| 동일 상품에 대해 서로 다른 5명이 신고 | 임계치(5) 도달 시 상품 자동 차단 | ✅ `report_count=5` → `status=blocked` |
| 관리자가 아닌 사용자가 `/admin/` 접근 | 403 | ✅ 403 |
| 관리자 로그인 후 대시보드/회원/상품 관리 접근 | 200, 정상 데이터 표시 | ✅ 정상 동작 |
| 로그인 실패 5회 반복 | 6번째 시도부터 "계정이 잠겨 있습니다" | ✅ 정상 동작 |
| 인증되지 않은 상태로 소켓 연결 시도 | 연결 거부 | ✅ 연결 실패("namespaces failed to connect") |
| 인증된 상태로 전체 채팅 메시지 송수신 | 정상 브로드캐스트 | ✅ 정상 동작 |
| 응답 헤더 확인 | CSP/X-Frame-Options/X-Content-Type-Options/세션 쿠키 HttpOnly+SameSite | ✅ 모두 확인됨 |

## 6. 유지보수

- **알려진 한계**: 로컬 개발 서버(Werkzeug) 기반 실행, SQLite 단일 프로세스 기준 동시성 처리, 인메모리 rate limit 저장소 — 모두 README의 "알려진 한계" 섹션에 명시했으며, 실사용 배포 시 각각 프로덕션 WSGI 서버/리버스 프록시, RDBMS 락, 공유 캐시(Redis)로 교체가 필요하다.
- **향후 개선 방향**: 상품 이미지 업로드, 알림 기능, 관리자용 신고 사유 통계, 채팅 메시지 신고 기능 등을 추가로 고려할 수 있다.
- **유지보수 프로세스**: 요구사항 변경이나 버그 발견 시 해당 기능이 속한 블루프린트 단위로 수정 후, `docs/security_checklist.md`의 관련 항목을 함께 재검토하도록 한다.

## 7. 개발 과정에서 확인한 보안 약점과 수정 내역

기준 코드(`ugonfor/secure-coding`의 `app.py`)를 그대로 두고 요구사항만 확장했다면 아래와 같은 보안 약점이 그대로 남아있었을 것이다. 각 항목에 대해 실제로 어떻게 수정했는지 정리했다.

| # | 기준 코드의 문제 | 위험성 | 본 프로젝트의 수정 |
|---|---|---|---|
| 1 | 비밀번호를 평문으로 `user.password`에 저장 | DB 유출 시 전 사용자 비밀번호 즉시 노출 | `bcrypt`로 salt 포함 해시 저장(`security.py`), 원문은 어디에도 저장하지 않음 |
| 2 | 모든 폼에 CSRF 토큰 없음 | 로그인된 사용자를 대상으로 한 CSRF 공격(의도치 않은 상품 등록/삭제 등) 가능 | `Flask-WTF CSRFProtect` 전역 적용, 모든 폼에 `hidden_tag()`로 토큰 삽입 |
| 3 | 세션 쿠키에 보안 옵션 없음 (`SECRET_KEY`도 하드코딩된 `'secret!'`) | 세션 탈취(XSS 연계) 및 시크릿 키 유출 시 세션 위조 가능 | 세션 쿠키 `HttpOnly`+`SameSite=Lax` (+운영 시 `Secure`), `SECRET_KEY`는 환경변수 전용으로 분리 |
| 4 | 로그인 실패 횟수 제한 없음 | 무차별 대입(brute-force) 공격에 취약 | 5회 실패 시 15분 계정 잠금 + IP 기반 로그인 rate limit, 아이디 존재 여부를 유추할 수 없도록 동일한 오류 메시지 사용 |
| 5 | 서버측 입력 검증 전무 (아이디/비밀번호/상품명 등 아무 값이나 허용) | 취약한 비밀번호, 형식에 맞지 않는 데이터 저장, 후속 XSS의 진입점 | `forms.py`/`security.py`에 정규식 기반 아이디·비밀번호 검증, 상품명/가격/신고사유 등 길이·범위 검증 추가 |
| 6 | 상품 수정/삭제 기능 자체가 없어 사실상 접근 제어 검증 대상이 없었음 | 기능 추가 시 소유자 검증을 빠뜨리기 쉬움(IDOR) | `edit_product`/`delete_product`에서 `product.seller_id == current_user.id` 명시적 검증, 불일치 시 403 |
| 7 | 신고 기능에 중복/남용 방지 로직 없음 | 동일인이 같은 대상을 반복 신고해 인위적으로 신고 수를 부풀릴 수 있음 | `Report` 테이블에 `UNIQUE(reporter_id, target_type, target_id)` 제약 + 신고 엔드포인트 rate limit |
| 8 | 신고가 쌓여도 아무 조치가 없음(수동 검토 로직조차 없음) | 악성 상품/유저가 방치됨 | 임계치(5회) 도달 시 자동으로 상품 차단/유저 정지 처리, 관리자 페이지에서 별도로 기각 가능 |
| 9 | 채팅이 인증 없이도 연결 가능, 메시지 검증/속도 제한 없음 | 비로그인 사용자의 스팸/도배, 서비스 거부(DoS)성 남용 | `connect` 이벤트에서 미인증 연결 차단, 메시지 길이 제한(500자), 사용자별 rate limit(10초당 8건) |
| 10 | 오류 발생 시 Flask 기본 디버그 페이지 노출(`debug=True` 고정) | 스택 트레이스, 내부 경로 등 민감 정보 노출 | 운영 설정(`ProdConfig`)에서 `DEBUG=False` 고정, 커스텀 에러 페이지(403/404/429/500)로 내부 정보 미노출 |
| 11 | 보안 헤더 전무 | 클릭재킹, MIME 스니핑 등에 취약 | `after_request`에서 CSP/X-Frame-Options/X-Content-Type-Options/Referrer-Policy 적용 |
| 12 | (신규 기능) 송금을 추가할 경우 자기 자신 송금·잔액 부족·정지 계정 송금 등을 놓치기 쉬움 | 잔액 위·변조, 정지된 사용자와의 비정상 거래 | 송금/구매 로직에 자기 자신 금지, 잔액 검증, 정지 계정 금지, 단일 트랜잭션 처리, 거래 로그를 모두 반영해 설계 단계부터 포함 |
| 13 | (신규 기능) 관리자 기능을 추가할 경우 관리자 계정을 코드에 하드코딩하기 쉬움 | 저장소가 공개(public)되는 순간 관리자 자격증명 유출 | `scripts/seed_admin.py`에서 환경변수로만 관리자 계정 생성, 소스코드·저장소에 자격증명 미포함(`.env`는 `.gitignore` 처리) |

## 8. 결론

기준 코드는 기능적으로는 요구사항을 만족하지만, 시큐어 코딩 관점에서는 인증/인가/입력 검증/세션 관리/오류 처리 등 거의 전 영역에서 보완이 필요했다. 이번 과제를 통해 "기능이 동작하는 것"과 "안전하게 동작하는 것"은 별개의 문제이며, 특히 신규 기능(송금/검색/관리자)을 설계할 때 처음부터 위협 시나리오(자기 자신 대상 행위, 권한 없는 접근, 남용/도배)를 고려해야 후속 보완 비용이 줄어든다는 점을 확인할 수 있었다.
